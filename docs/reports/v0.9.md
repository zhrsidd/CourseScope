**21 verified 2027 applications** across three families, each read individually:

## 6. Report-an-error flow and feedback destination

`src/components/ReportIssue.tsx` routes by configuration, with three honest states:

```
VITE_FEEDBACK_URL set   → 'form'       submits to that form
VITE_FEEDBACK_EMAIL set → 'email'      opens a prefilled mail draft
neither set             → 'copy-only'  shows the report and says there is nowhere to send it
```

Seven issue types. The generated report carries university, course, award, entry year, UCAS code, record ID, trust state, source URL, last-checked date, build version and the page the user was on — so a report is actionable without a follow-up question.

**No personal email is hardcoded.** `.env.example` documents the variables using a placeholder on `example.org` only.

**Current state: `copy-only`.** Neither variable is set, so the deployed build has nowhere to send a report. Per Part 6 this must be reported as HIGH or BLOCKER "depending on whether the UI appears functional". The UI **does not** present a fake submit action: there is no disabled-looking Send button, no spinner, no success message. It shows the composed report, offers to copy it, and says plainly that no destination is configured. That is the honest behaviour Part 6 asked for, so this is classified **HIGH** — a launch setup step requiring explicit acceptance, not a blocker. See §20.

## 8. Production metadata and SEO

Static, in `index.html` so a non-JavaScript crawler still sees it: expanded description, `theme-color`, robots meta, an inline SVG favicon, and Open Graph + Twitter card tags.

Runtime, in `src/lib/site-meta.ts`, called once from `main.tsx`: `<link rel="canonical">` and `og:url`, **added only when `VITE_SITE_URL` is set**.

Two deliberate omissions, both documented in the source:

- **No canonical tag today.** A relative canonical is meaningless and a guessed absolute one actively tells crawlers that some other page is the real one. With no domain configured the correct number of canonical tags is zero. (An earlier attempt at `<link rel="canonical" href="/">` also broke the build outright — Vite resolved `/` as an asset and failed with `EISDIR`.)
- **No `og:image`.** It needs an absolute URL to a hosted file, and the only honest image today would be a screenshot of a catalogue still being completed. Text-only share cards degrade cleanly everywhere, so the cost is a thumbnail, not correctness.

## 10. Deployment readiness

The app is a **static site** — no server, no API, no build-time fetching. The whole catalogue is bundled.

**Hash routing is retained deliberately.** Every route lives after a `#`, so the browser only ever requests `/index.html`. Deep links therefore work on any static host with **no rewrite rules at all** — no `_redirects`, no `try_files`, no 404-to-index trick. The cost is a `#` in every URL and one crawlable page. Browser-history routing would fix both and would require host-specific rewrite configuration that cannot be tested against a real host from here, so v0.9 does not migrate the routing architecture for appearance. The tradeoff is documented in `vite.config.ts` and recorded in §19.

**Base path defaults to `./`**, so `dist/` works from a domain root, a subdirectory, or the filesystem without rebuilding.

`README.md` carries a release-status table, `npm ci`-based verification steps, the configuration table, the deployment note and the admin-route note.

## 12. Fresh-state and persistence QA

**One BLOCKER was found and fixed here.** A legacy `ukcf.profile.v1` value written by an older build parsed as valid JSON but had the wrong shape, and a consumer reading `profile.aLevels` on it took the whole app to a blank white page:

```
TypeError: Cannot read properties of undefined (reading 'filter')
```

The realistic victim is not a hostile user — it is an ordinary one returning after a few months to a blank page with nothing to click.

`useLocalStorage` now treats the stored value as untrusted: a parsed value must pass a caller-supplied `isValid` shape check, and anything failing is discarded in favour of the initial value. **Only the failing key resets** — each piece of state has its own key and its own validator, so a corrupt profile no longer clears a good shortlist. The discarded value is not written back until the user changes something, so a read-only visit leaves their old data alone. `isStudentProfile()` in `src/lib/grades.ts` does the structural check; `isStringArray()` guards the saved-ID lists.

QA covers a brand-new visitor's full 12-step flow with zero stored state, plus **four legacy-storage cases** — all four now boot.

## 14. Mobile and responsive QA

Verified at **390px, 820px and 1440px**, on every route, with tooltips both closed and open: **0px horizontal overflow everywhere.**

This took three attempts and the first two were wrong, so the root cause is documented in `InfoTooltip.tsx`. v0.8 fixed a 197px overflow by anchoring the panel to the right on small screens; v0.9 found **147px still overflowing on course pages at 390px and 75px at desktop width**. Two separate faults:

1. An absolutely positioned element **contributes to document scroll width even at `opacity: 0`** — a page of closed tooltips could be dragged sideways before anyone touched anything. The panel is now **not rendered at all when closed**.
2. **There is no correct side to anchor to.** Left-anchored overflows near the right edge; right-anchored overflows near the left. When open, the panel now **measures its own bounding box and shifts horizontally** to sit inside the viewport, which works at any width, on either side, for any trigger position.

**`npm audit`: 4 advisories — 1 high, 3 moderate. All are build tooling, none is exploitable in a deployed static site.**

- **vite (high)** — path traversal in optimized-deps `.map` handling, plus two Windows-specific `server.fs.deny` bypasses. All are **dev-server** issues. There is no dev server in production.
- **esbuild (moderate)** — any website can send requests to the **development server**. Same reasoning.
- **react-router / react-router-dom (moderate)** — open redirect via backslash in `<Link>`/`useNavigate`, and arbitrary constructor injection in `deserializeErrors()` during **SSR hydration**. This app has no SSR, and it does not construct routes from user input or external data: every link target comes from the bundled catalogue.

Recommendation: take the upgrades on the first post-v1 maintenance pass. None of them justifies delaying the release, and none of them justifies claiming the audit is clean — it is not, it is *not applicable*, which is a different statement.

### READY FOR v1.0.0

Recommended release sequence:

1. **Set `VITE_FEEDBACK_URL` or `VITE_FEEDBACK_EMAIL`** (resolves H1) and **`VITE_SITE_URL`** (resolves H2) in the production environment. Both are configuration, not code.

4. **Run `npm run release:verify` and `npm run qa` once more against the tagged build** with the production variables set, so the deployed configuration is the configuration that was tested.
5. **Publish the production deployment** of `dist/` to any static host — no rewrite rules needed.
6. **Publish the v1 release notes** from `RELEASES[]`, which are already written for students and contain no unsupported claims.

The six `awaiting-data` records and the seven items in §19 are the v1.1 backlog. None of them is a reason to hold v1.0.0.
